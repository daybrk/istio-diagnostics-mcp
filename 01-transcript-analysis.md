# Разбор монолога: MCP для расследования инцидентов Istio

Дата: 23 октября 2026 года.  
Статус: фиксация и анализ замысла по предоставленной текстовой расшифровке. Это не описание уже реализованного поведения и не утверждённая спецификация API.

Связанный документ: [предложения по улучшению](02-algorithm-improvements.md).

## 1. Суть замысла

Нужен MCP-сервер, который помогает клиентскому агенту расследовать проблемы взаимодействия приложений в Kubernetes с Istio. Пользователь формулирует проблему на естественном языке, например: приложение A в namespace A не может обратиться к приложению B в namespace B.

Сервер предоставляет инструкции и инструменты доступа к диагностическим данным. Агент организует расследование, анализирует наблюдения, при необходимости привлекает сабагентов и ASTRA, затем объясняет пользователю найденную проблему и предлагает решение.

Основная идея монолога — пройти от состояния окружения к конфигурации маршрута, затем к логам и требованиям самого продукта.

## 2. Разделение ролей, которое следует из монолога

| Участник | Предполагаемая роль |
|---|---|
| Пользователь | Описывает сбой взаимодействия A → B; получает объяснение и предложение решения |
| Основной агент клиента | Получает алгоритм через MCP, выбирает инструменты, сопоставляет данные и формирует итог |
| MCP-сервер | Предоставляет entry point, инструкции и инструменты получения данных Kubernetes/Istio, логов, config dump и контекста ASTRA |
| Сабагенты клиента | Анализируют логи отдельных pod’ов и возвращают результаты основному агенту |
| Kubernetes, Istio, Envoy | Источники состояния объектов, настроек и наблюдаемого поведения |
| ASTRA | Источник знаний о продукте, его настройках, зависимостях и предполагаемом взаимодействии компонентов |

В монологе не сформулирована необходимость отдельной LLM внутри Go-сервера. Упоминания агента и сабагентов относятся к стороне клиента; это согласуется с предыдущим обсуждением проекта.

## 3. Алгоритм в исходном порядке

### 3.1. Обращение пользователя и entry point

Пользователь сообщает о невозможности взаимодействия приложений. Агент обращается к входному инструменту MCP и получает промпт, который объясняет:

- как взаимодействовать с пользователем;
- какие инструменты MCP использовать и в каком порядке;
- как работать с Istio-конфигами, config dump и логами;
- как привлекать ASTRA и интерпретировать её ответы;
- какие действия допустимы и запрещены с точки зрения кибербезопасности.

### 3.2. Первичный осмотр окружения

Агент через MCP получает описания namespaces A и B, pod’ов обоих приложений и относящихся к ним ingress/egress-компонентов. Выполняет поверхностные проверки состояния: запущены ли pod’ы, как namespaces подключены к Istio, согласована ли используемая control plane.

Затем отдельно проверяет работоспособность Istiod. В монологе для этого предполагается инструмент MCP.

### 3.3. Получение config dump

Если первичные проверки не объяснили проблему, агент получает dump прокси приложений и ingress/egress-прокси. По дампам строит топологию прохождения запроса и извлекает сведения о связанных Istio-конфигурациях.

### 3.4. Получение и сравнение Istio-конфигураций

Агент запрашивает через MCP конфиги, которые удалось связать с dump. Строит по ним второе представление топологии и сравнивает его с представлением из прокси.

Если обнаружены расхождения, исследует их причины. При отсутствии объясняющих расхождений переходит к логам.

### 3.5. Анализ логов

Исследуются логи приложений A и B и участвующих gateway-компонентов. Предложена схема «один сабагент на pod»: каждый сабагент ищет ошибки и возвращает заключение по своему участнику.

Основной агент объединяет эти заключения и пытается установить, какие из найденных ошибок объясняют исходный сбой.

### 3.6. Привлечение ASTRA

Если предыдущие этапы не дали объяснения, агент обращается к знаниям о приложениях A и B в ASTRA. Пример смыслового запроса: как должно быть настроено приложение A, чтобы оно могло обращаться к приложению B.

Ответ сопоставляется с фактическими настройками приложений. Обнаруженные различия или конфликты становятся основанием для предложения пользователю проверить или изменить конкретную настройку.

### 3.7. Завершение

Агент сообщает найденную проблему и предлагаемое решение. Если имеющихся средств и данных недостаточно для объяснения, сообщает об этом ограничении.

В конце прозвучало краткое обсуждение событий и отрицательный ответ. Для этой фиксации это интерпретируется как исключение Kubernetes Events из предлагаемого сценария. Аудиофайл отдельно не анализировался; основание — доступная расшифровка и последующее резюме разговора.

## 4. Что требуется от системы

| ID | Требование из монолога | Ожидаемый результат |
|---|---|---|
| M01 | Понятная входная точка MCP | Агент получает алгоритм и правила начала исследования |
| M02 | Инструкции по работе с данными и пользователем | Агент понимает назначение результатов инструментов |
| M03 | Получение описаний объектов окружения | Доступны состояния namespaces, приложений и gateway-компонентов |
| M04 | Проверка Istiod и подключения к Istio | Доступны сведения о control plane и её связи с участниками |
| M05 | Получение config dump | Доступна конфигурация исследуемых прокси |
| M06 | Построение топологии из dump | Видны предполагаемые переходы запроса между компонентами |
| M07 | Получение связанных Istio-ресурсов | Доступны исходные декларативные настройки |
| M08 | Сравнение представлений топологии | Выделены расхождения, требующие объяснения |
| M09 | Анализ логов всех участвующих pod’ов | Основной агент получает результаты по каждому участнику |
| M10 | Использование ASTRA для требований продукта | Доступно описание ожидаемых настроек и зависимостей |
| M11 | Сопоставление требований с настройками приложений | Выделены нарушения или противоречия |
| M12 | Итог с рекомендацией | Пользователь получает объяснение и следующий шаг |

M06–M08 описывают желаемый результат, но ещё не определяют алгоритм построения графа и правила установления причинности.

## 5. Решения из предыдущего обсуждения

Эти пункты важны для проекта, но не следует выдавать их за новые требования, впервые прозвучавшие в монологе:

- MCP реализуется на Go; отдельный серверный агент не обязателен.
- ASTRA остаётся опциональной. Пользователь может передать project ID агенту для текущего исследования.
- Период исследования выбирает пользователь; он не ограничен 15 минутами.
- Инструкции удобнее разбивать на связанные модули, чем передавать одним большим промптом.
- Серверный namespace allowlist удалён. Сохраняются ограничения по разрешённым Kubernetes contexts и фактическим правам kubeconfig.
- Предыдущий эксперимент показал проблему клиентской сериализации и повторных неудачных вызовов. Поведение при таких ошибках является отдельной частью надёжности системы.

## 6. Места, требующие технической конкретизации

Здесь зафиксированы пробелы постановки. Это не вопросы пользователю и не дополнительные согласованные требования.

| Формулировка | Что пока не определено |
|---|---|
| «Панель» на namespace | Вероятно, имеется в виду control plane Istio, но термин в расшифровке неоднозначен |
| «Istio вода» | В этом разборе интерпретируется как Istiod; точная формулировка в тексте искажена |
| «Ingress/egress namespace’а» | Как находить gateway, доказать его участие в связи и учесть расположение в другом namespace |
| «Построить топологию» | Набор узлов и связей, учёт портов, протоколов, Host/SNI, TLS и ветвящихся маршрутов |
| «Имена конфигов из dump» | Как восстанавливать происхождение конфигурации и обрабатывать отсутствующие связи с исходными ресурсами |
| «Получить конфиги приложения» | Какие источники разрешены, как учитывать ConfigMap/env/аргументы запуска и не читать секреты |
| «Один сабагент на pod» | Лимит параллелизма, формат результата, повторное использование данных и работа клиента без сабагентов |
| «Если всё хорошо» | Проверка может завершиться успешно, частично, без данных или с неподдержанной семантикой |
| «Решить проблему» | В монологе не задано право автоматически применять изменения; конечный результат описан как рекомендация |
| «Обратиться к ASTRA для A и B» | Как явно связать каждый компонент с выбранным пользователем проектом и нужной версией документации |

## 7. Аналитическая оценка исходного алгоритма

### Сильные стороны

1. Исследование охватывает инфраструктуру, конфигурацию прокси, наблюдаемые ошибки и требования приложения.
2. В центре находится связь между двумя приложениями, а не случайный набор ошибок всего кластера.
3. Предусмотрено сопоставление декларативных настроек с состоянием прокси.
4. Логи анализируются по участникам, что позволяет заметить разные симптомы на разных сторонах.
5. ASTRA используется как источник продуктовых знаний, которых может не быть в Kubernetes-ресурсах.
6. Пользователь получает не только найденную ошибку, но и предлагаемое действие.

### Основные риски

| Риск | Возможное последствие |
|---|---|
| Логи откладываются до завершения разбора dump | Очевидный симптом обнаруживается поздно, выполняются лишние чтения |
| Конфиги выбираются исключительно по присутствию в dump | Отсутствующие или неприменившиеся настройки могут остаться вне исследования |
| Успех одного этапа трактуется как исправность всего слоя | Неполное покрытие превращается в ложный вывод |
| Нет ошибок в логах → проблема в настройках приложения | Причина назначается методом исключения без достаточных доказательств |
| Неограниченное количество сабагентов | Рост времени, стоимости и повторяющихся запросов |
| Правила безопасности существуют только в промпте | Фактические действия зависят от дисциплины клиента |
| Время dump и время инцидента не различаются | Текущее состояние ошибочно используется как доказательство прошлого |

Эти риски не отменяют замысел. Они показывают, какие условия нужно добавить к переходам между этапами и к формированию вывода.

## 8. Граница этого документа

Документ фиксирует смысл предоставленной расшифровки и связанные договорённости. Он не утверждает, что все перечисленные инструменты уже существуют, что полная топология всегда восстанавливается или что автоматическое исправление разрешено.

Конкретные предложения по алгоритму, структуре данных, ограничениям и проверке результата вынесены в [отдельный документ](02-algorithm-improvements.md).
