# istio-diagnostics-mcp: диагностика east-west соединений

Дата: 22 октября 2026 года.
Статус: проектное описание для проверки пользователем перед планом реализации.
Архивная основа: прототип на Go, commit `45ea784`, PR #1.
Прототип сохранён в `archive/go-mcp-v0.1`; рабочая ветка `feat/go-mcp-v0.1` очищена от его кода.
[Решение об очистке](../../design/rewrite-baseline.md).

Подробные контракты, модульные промпты, каталог правил и критерии проверки собраны
в [проектном комплекте](../../design/README.md). Этот документ сохраняется как
обзор договорённостей. Точные поля API и новые предлагаемые детали перечислены
в комплекте; целевой набор включает 11 tools, а не семь tools прототипа.

Документ описывает переработку текущего проекта. Это целевое поведение, а не
перечень уже реализованных возможностей. Согласованные пользовательские решения
зафиксированы в разделах 1–4. Устройство компонентов и интерфейсов ниже —
предлагаемое техническое решение, входящее в эту проверку документа.

## 1. Назначение и границы

MCP помогает ответить, почему приложение не может подключиться к другому
приложению или почему другое приложение не может подключиться к нему. Результат
должен связывать конкретный симптом с доказательствами, областью воздействия и
рекомендацией по исправлению. Если причины установить нельзя, это самостоятельный
корректный результат с объяснением недостающих данных.

Согласовано:

- Go, запуск снаружи кластера через kubeconfig; два способа подключения:
  локальный stdio и удалённый Streamable HTTP.
- Единственный пользовательский режим — live read-only.
- Один Kubernetes-кластер, Istio sidecar, east-west между приложениями;
  разрешены разные namespace внутри доступной области.
- HTTP, HTTPS, gRPC и raw TCP, включая соединения с БД и брокерами.
- Логи контейнера `istio-proxy`, все pod'ы выбранного приложения.
- Сбор конфигурации через временный port-forward к порту pod'а `15000` и HTTP GET.
- Без изменения ресурсов, перезапусков, pods/exec и активных запросов к приложению.
- Пользователь выбирает проблемное направление, затем может исследовать следующее
  или закончить сессию. Конкретную заранее указанную связь исследуем сразу.
- Сначала короткий вывод; технические подробности предоставляем по запросу.
- ASTRA-SBT — необязательная интеграция для контекста продукта. Основная
  диагностика Kubernetes/Istio работает без неё.

За пределами этого объёма: внешний egress, ingress от внешнего клиента, ambient,
multicluster, UDP, воспроизведение исторических конфигураций, автоматическое
исправление и непрерывный мониторинг. Если обнаружен такой участок, результат
содержит границу покрытия, а не выдуманное продолжение пути.

Внутренние фикстуры для тестов и чистые функции анализа сохраняются. Загрузка
пользовательских dump-файлов и offline CLI перестают быть продуктовым сценарием.

## 2. Что известно и что пока предполагается

Пользователь подтвердил kubeconfig, чтение необходимых ресурсов и использование
port-forward. Переданная HTML-страница с порта `15000` — меню Envoy Admin;
в ней присутствует встроенный `config_dump` с `include_eds`. Отдельный handler
в приложении создавать не нужно. Это подтверждает интерфейс, но не является
проверкой доступа MCP к реальному кластеру.

Для проектирования принято, что access logs доступны. Реальный образец логов,
версии Istio/Envoy и доступность каждого поля ещё не проверены. Поэтому парсер
должен обнаруживать поддерживаемый формат и сообщать о пропусках. Наличие
контейнера `istio-proxy` само по себе не подтверждает наличие access logs.

## 3. Ввод, направление и время

Перед сбором однозначно определяются Kubernetes context, namespace выбранного
приложения и само приложение. Context можно взять из явно настроенного MCP;
если вариантов несколько и выбор не задан, требуется уточнение.

Приложение задаётся именем Deployment/StatefulSet, именем pod'а или label selector.
Существующий способ разрешения DaemonSet можно сохранить. Pod служит точкой
идентификации: при известном владельце определяется приложение и его реплики.
Самостоятельный pod образует приложение из одного pod'а. При нескольких
кандидатах возвращается выбор, а не первый найденный объект. Namespace не
подставляется как `default` без основания.

Направление берётся из формулировки пользователя:

| Формулировка | Источник | Назначение |
|---|---|---|
| «Из A недоступен B» | A | B |
| «К A не может подключиться B» | B | A |
| «У A что-то с сетью» | Требует уточнения | Требует уточнения |

Назначение может быть приложением, Service, host/FQDN или IP. Порт и протокол
извлекаются из сообщения и наблюдений; при влияющей на вывод неоднозначности
задаётся уточнение. Указание обоих приложений без порта не требует лишнего вопроса,
если в данных есть единственное подходящее направление.

Пользовательский период всегда приоритетен. Допускаются относительная длительность
и конкретные начало/конец. По умолчанию — последние 15 минут. Относительный
период один раз преобразуется в абсолютный интервал `[start, end)` при начале
попытки; все участники проверяются за него. Неоднозначные дата и часовой пояс
уточняются; внутри используются RFC3339/UTC, в ответе показывается понятная зона.

Окончание интервала фильтруется локально после чтения логов с нижней границей.
Сохраняются время события, время записи и источник timestamp, если они доступны.
Длительный TCP-сеанс или запрос мог начаться до окна и завершиться внутри него;
такие пересечения учитываются при наличии duration. Неполноту наблюдения за
долгими/незавершёнными соединениями явно отмечаем.

Увеличение периода не означает восстановление удалённых или ротированных логов.
Самая ранняя полученная строка не доказывает начало хранения. Отдельно возвращаются
запрошенный период, наблюдаемый диапазон событий и известные ограничения сбора.
Все конфигурации имеют собственное время сбора и описывают текущее состояние.
Сбор нескольких ресурсов не атомарен. Видимый разрыв ссылок во время rollout
перепроверяется ограниченным повторным чтением; при сохраняющейся неоднозначности
он не превращается в подтверждённый конфликт.

## 4. Диагностическая сессия

Выбран подход «симптомы → проверка конфигурации». Полный аудит приложения при
каждом запросе создаёт лишний объём; обязательная точная пара заранее не помогает
при общей жалобе. Эти два варианта не являются основным сценарием.

Общий сценарий:

1. Уточнить приложение, namespace, направление и период.
2. Собрать логи всех его pod'ов и построить список проблемных направлений.
3. Показать источник, назначение, порт/протокол, признаки ошибок, число наблюдений,
   затронутые pod'ы и последнее событие.
4. Получить выбор пользователя и исследовать выбранное направление.
5. Выдать краткий результат и предложить оставшийся список либо завершение.

Для конкретной пары шаг выбора списка пропускается. Если внутри пары есть
существенно разные порты или назначения, уточняется только эта неоднозначность.

Список группируется сначала по связи источник → назначение, порту и протоколу;
внутри сохраняются отдельные сигнатуры ошибок и различия реплик. Неизвестные
источники/назначения не исчезают из списка. У направлений стабильные ID, чтобы
пагинация и сортировка не меняли выбор. Количество строк логов не называется
количеством уникальных пользовательских запросов без надёжной дедупликации.

Просмотренное направление получает статус `investigated`, который не означает
«исправлено». Сохраняются результат и оставшаяся очередь; доступны возврат к
результату и повторный сбор. Обновление после воспроизведения ошибки создаёт
новую попытку со своим периодом и evidence, не перезаписывая прежние выводы.
Новый период применяется явно, а исходный исторический интервал не сдвигается.

## 5. Расследование выбранной связи

### 5.1. Участники и сбор

Для исходящей жалобы отправной точкой служат логи источника, для входящей —
логи назначения. По owner references, Service, EndpointSlice и данным прокси
устанавливается противоположная сторона. При необходимости читаются ресурсы
другого разрешённого namespace. Внешний host не резолвится локальным DNS машины
MCP как будто это DNS приложения.

Состав pod'ов фиксируется с UID и временем обнаружения. Планируется чтение всех
доступных pod'ов участвующих приложений; нет скрытой выборки одной реплики.
Сохраняются результаты по каждой реплике. Удалённый pod, отказ RBAC или таймаут
отмечаются как пробел. При рестарте читаются доступные previous-логи прокси.

Сначала собираются логи и ресурсы. После выбора связи собираются dump'ы всех
доступных прокси участвующих приложений с ограниченной параллельностью. Нет
обхода всех прокси кластера и нет перебора всех пар реплик. Наблюдавшиеся upstream
адреса связывают события с конкретными получателями, остальные реплики остаются
кандидатами с отдельной оценкой конфигурации.

### 5.2. Нормализация симптомов

Из доступных полей выделяются timestamp, pod/container identity, направление,
downstream/upstream адреса, host/authority, upstream cluster, порт, протокол,
HTTP/gRPC status, response flags/details, transport failure reason, duration и
request ID. Отсутствующее поле остаётся неизвестным, а не нулём или успехом.

Первоначальные адаптеры: стандартный текстовый access log Istio и JSON с известным
или явно заданным соответствием полей. Если формат неизвестен, сохраняется статус
неподдерживаемого разбора и ограниченный очищенный пример. Произвольная строка
со словом ERROR не превращается автоматически в ошибку конкретного соединения.

HTTP 4xx/5xx — признаки проблемного ответа, а не автоматическое доказательство
сбоя сети. Отделяем local reply прокси от ответа upstream. Для gRPC учитываем
gRPC status при наличии; HTTP 200 не означает успешный RPC. Для зашифрованного
passthrough и TCP не выдумываем невидимые HTTP-поля или детали SQL/протокола БД.

### 5.3. Корреляция

Сопоставляем события по совокупности request/trace ID, участников, upstream адреса,
времени, порта и других доступных атрибутов. Совпадение одного времени или одного
ID не гарантирует единственный запрос: возможны retry, повторное использование
ID, clock skew и несколько попыток upstream. TCP сопоставляется как соединение,
когда для этого достаточно адресов и времени; иначе это только кандидат.

Отсутствие события на принимающей стороне не доказывает, где оборвалось соединение.
Текущий Pod IP или состав endpoints не считается достоверной исторической
идентичностью без дополнительного основания.

### 5.4. Путь и проверки

Проверяем активный путь источника: listener → filter chain → HTTP route или
TCP proxy → cluster → endpoints; затем соответствующий входящий путь назначения
и локальный upstream к приложению. Используем фактические адреса/порты для каждого
участка, различая Service port, targetPort и порт приложения.

| Область | Что проверяется | Граница вывода |
|---|---|---|
| Service/endpoints | Селекторы, named targetPort, EndpointSlice, readiness, subsets | Endpoint в списке не доказывает, что процесс слушает порт |
| Routing | Listener/filter chain, host/SNI/ALPN, route, cluster refs, visibility, weighted branches | Без необходимых атрибутов сохраняются кандидаты или UNKNOWN |
| Конфликты | Применимые пересечения host/port/protocol, затенение маршрутов, активная конфигурация и rejected updates | Одинаковый порт у разных Service сам по себе не конфликт |
| TLS/mTLS | Ссылки SDS, доступные сроки/identity/trust metadata, режимы обеих сторон, ошибки handshake | Истёкший неиспользуемый сертификат не причина выбранного сбоя |
| Istio access control | Применимые AuthorizationPolicy, PeerAuthentication, RequestAuthentication и активные фильтры | Недоступная identity, CUSTOM auth или неподдерживаемая семантика дают UNKNOWN |
| NetworkPolicy | Применимость к источнику/назначению, обе стороны, доступные selectors и порты | Статический вывод по политике не подтверждает применение CNI или состояние сети |
| Состояние прокси | Ошибки xDS, active/warming, различия реплик, доступное состояние clusters | Отклонённое обновление не означает автоматически поломку активного пути |
| Приложение | Connection refused/reset, timeout, ответы upstream | Кто занимает порт и состояние socket нельзя установить только по dump |

Читаются применимые ресурсы Istio, включая Sidecar, VirtualService, DestinationRule,
ServiceEntry, EnvoyFilter и security policies. При необходимости учитываются
root namespace и экспортированные cross-namespace ресурсы; если они недоступны,
полнота политик не заявляется. Неподдерживаемый matcher, Lua/Wasm, нестандартный
фильтр или неизвестная версия явно останавливают затронутый вывод.

Проблемы DNS до попадания обращения в sidecar могут не иметь access log.
Проверяем доступные имена, Service и настройки, но не объявляем DNS исправным
по отсутствию ошибок. Аналогично timeout без дополнительных свидетельств не
доказывает NetworkPolicy, CNI, отказ процесса или конкретный межузловой сбой.

### 5.5. Вывод и отсутствие симптомов

Каждая находка содержит факт, связь с выбранным соединением, доказательства,
затронутые реплики, оценку достоверности, рекомендацию и способ её проверки.
Статусы причин: `confirmed`, `probable`, `unknown`; статус отдельной проверки
сохраняет `PASS`, `FAIL`, `UNKNOWN`, `UNSUPPORTED`.

Для `confirmed` нужны непосредственное свидетельство механизма отказа и надёжная
привязка к выбранному событию/участку. Подтверждение отказа Envoy не означает
автоматического подтверждения конкретного YAML как его источника. Причины разных
реплик или попыток могут различаться; первая находка не прекращает расследование.

Если нужных событий нет, выполняются доступные проверки конфигураций обеих сторон,
endpoints, портов и TLS. Ответ сообщает: «Неудачное соединение в логах не найдено;
причину сбоя пока подтвердить нельзя». Предлагается повторить запрос пользователю
и заново собрать данные. Сам MCP запрос не выполняет и не объявляет связь здоровой.

## 6. Сбор и модель доступа

Сохраняем подход текущего проекта с фиксированными командами `kubectl`, аргументами
без shell и ограничениями времени/объёма. Зависимость от `istioctl proxy-config`
заменяется управляемым port-forward и Go HTTP-клиентом.

Port-forward выбирает конкретный pod и свободный локальный порт, слушает только
`127.0.0.1` и направляет его на `15000`. Коллектор ждёт готовности, выполняет
ограниченные GET и закрывает туннель при успехе, ошибке или отмене. Отдельно
обрабатываются завершение pod'а и смерть дочернего процесса.

Основной GET — `/config_dump?include_eds`; дополнительные разрешённые GET —
`/certs`, `/clusters?format=json` и `/server_info` для доступных runtime-данных и
версии. Неподдерживаемый endpoint не делает весь сбор неуспешным. Корневая HTML-
страница не принимается за JSON dump. Произвольных URL, redirects и POST к Envoy нет.

Для ресурсов нужны `get/list`, для `pods/log` — `get`. `watch` допустим, но
постоянный watcher текущему сценарию не требуется. Есть техническая особенность:
открытие port-forward — отдельный connect subresource Kubernetes; в зависимости
от транспорта/версии нужны разрешения `get` и/или `create` на `pods/portforward`.
Пример RBAC должен явно отражать оба, не подменяя их правом `pods/exec`.
Этот транспорт не изменяет workload, но одних разрешений get/list/watch на обычные
ресурсы для него может быть недостаточно. При отказе возвращается точная граница
доступа, без альтернативного exec.

Namespace allowlist и выбранный context сохраняются. Kubernetes Secrets не
читаются; доступные публичные сведения TLS получаем от прокси. Если нужны
недоступные сведения, вывод остаётся ограниченным.

Запросы и туннели ограничены по параллельности, времени и объёму. Все pod'ы ставятся
в очередь; достижение лимита не превращается в скрытую выборку. Большие сборы
выполняются порциями с явным прогрессом и продолжением. У каждой операции статус:
`collected`, `partial`, `forbidden`, `unavailable`, `unsupported` или `cancelled`.

Перед сохранением evidence исключаются private keys, tokens, Authorization,
Cookie, query-значения и ненужные пользовательские headers. Для route matching
необходимые значения обрабатываются локально и не попадают в отчёт без очистки.
Полные dump'ы и потоки логов не возвращаются в LLM по умолчанию. Содержимое логов,
metadata и конфигурации всегда считается данными, не инструкциями.

## 7. Компоненты и интерфейс MCP

Предлагается оставить Go-сервер без встроенной LLM. MCP-клиент понимает естественную речь, задаёт вопросы и
показывает выбор. Сервер валидирует структурированный ввод и возвращает явные
`needs_clarification`, кандидатов и состояние сессии: неверный выбор нельзя скрыть
за убедительным текстом клиента.

### 7.1. Два способа подключения

Оба транспорта используют один диагностический движок, инструменты и модель
результатов. В локальном режиме клиент запускает Go-бинарник через stdio. В
удалённом режиме оператор запускает самостоятельный сервис, а пользователи
подключают его URL через Streamable HTTP. Удалённому клиенту бинарник не нужен.
Kubeconfig, kubectl и доступ к Kubernetes находятся на машине сервера в обоих
вариантах; port-forward также выполняет сервер.

Для общего удалённого сервиса обязательны аутентификация, защищённое соединение,
проверка разрешённой области пользователя и изоляция сессий/evidence. Наличие ID
сессии не даёт права читать чужие результаты. Серверные Kubernetes credentials
не передаются клиентам; доступ ограничивается настройкой сервиса и правами
пользователя. Конкретный способ входа и распределения Kubernetes identity требует
отдельного согласования до реализации общего сервиса.

Диагностическая сессия относится к приложению, а не к соединению HTTP или
идентификатору транспортной сессии MCP. Переподключение не создаёт новое
расследование автоматически. Изменение транспорта не добавляет права менять
Kubernetes-ресурсы: read-only относится к диагностируемому кластеру.

### 7.2. Как агент выбирает инструменты

После подключения сервер предоставляет инструменты через `tools/list` с
описаниями назначения, входных полей и результатов. В описании `start_diagnosis`
явно перечисляются жалобы на входящие/исходящие соединения Kubernetes/Istio.
Инструкции сервера задают правила уточнения namespace, направления и периода,
выбора связи и представления доказательств. Их передача модели зависит от клиента;
встроенные подсказки результата дополняют общие инструкции.

Результаты содержат состояние, недостающие поля, кандидатов и допустимое следующее
действие. Это наш прикладной контракт поверх MCP. При `needs_clarification`
возвращается точный вопрос; при `awaiting_selection` — направления для выбора;
при `awaiting_next` — результат и оставшаяся очередь. Клиент не должен угадывать
последовательность по названиям инструментов или читать README для её выполнения.
Сервер проверяет вход и переходы состояния независимо от формулировок модели.

### 7.3. Координатор и LLM-агент

Координатор на Go автоматически планирует необходимые чтения для выбранной связи,
собирает данные обеих сторон, запускает проверки, ограничивает повторные сборы
и строит результат. Клиентскому агенту не требуется вызывать отдельный инструмент
для каждого listener, сертификата или pod'а. Остановка для пользовательского
выбора остаётся частью согласованного сценария.

Рекомендация для текущего объёма — один LLM-агент на стороне клиента и серверный
координатор с проверяемыми правилами. Дополнительный серверный LLM-агент создаёт
ещё один цикл выбора действий, модельную зависимость, расходы и задержку; его
полезность для согласованных проверок пока не показана. Он может быть оправдан
при отдельном требовании к самостоятельному исследованию нестандартных случаев
или работе без клиентского агента. Эти возможности в текущий объём не включены.

### 7.4. Компоненты и инструменты

| Компонент | Ответственность | Зависимости |
|---|---|---|
| `server` | Типизированные инструменты, контракты, отображение ошибок | Coordinator |
| `session` | Область, окно, очередь, попытки, результаты и время жизни | Evidence store |
| `live` | Kubernetes GET/logs, управление port-forward, чтение Envoy | Runner, HTTP client, clock |
| `logs` | Парсинг, нормализация, классификация, группировка | Чистые модели событий |
| `diagnostics` | Проверки пути, ресурсов, TLS/policy и связь evidence | Чистые модели данных |
| Coordinator | Сбор для выбранной связи и построение отчёта | Остальные компоненты |

Подходящие части архивного `diagnostics` можно переносить выборочно после проверки
по новому контракту. Сбор и выбор причин не смешиваются с чистым разбором Envoy JSON.

Предлагаемые публичные инструменты:

| Инструмент | Назначение |
|---|---|
| `get_capabilities` | Доступная область, поддержка форматов/проверок, лимиты |
| `resolve_workload` | Кандидаты по имени/pod/selector с namespace и UID |
| `start_diagnosis` | Создать сессию; при однозначной паре сразу начать расследование, иначе собрать очередь |
| `get_diagnosis` | Получить прогресс, краткие результаты и страницу оставшейся очереди |
| `investigate_connection` | Исследовать выбранный ID или однозначную явно заданную связь |
| `get_evidence` | Получить очищенные подробности конкретного результата |
| `refresh_diagnosis` | Создать новую попытку сбора, явно сохранив или изменив период |
| `close_diagnosis` | Завершить сессию и освободить её рабочие данные |
| `cancel_operation` | Отменить job, сохранив сессию и частичный результат |
| `get_playbook` | Получить модуль инструкций закреплённой версии |
| `get_product_context` | Необязательные каталог/вопрос/поиск/чтение через ASTRA |

Состояния: `needs_clarification`, `collecting`, `awaiting_selection`,
`investigating`, `awaiting_next`, `closed`. Длительная операция возвращает ID и
прогресс; последующие чтения показывают тот же job, не запускают дубликат.
Повторные изменяющие сессию вызовы используют operation ID для защиты от дублей.
Отмена прекращает текущий сбор и сохраняет доступный частичный результат.

Сессии и evidence хранятся в памяти с настраиваемыми лимитами и idle TTL; исходное
предложение — 30 минут простоя, до 16 сессий и общий предел памяти 256 MiB.
Эти лимиты не ограничивают выбранный исторический период. Прогресс обновляет
активность сессии. При лимите возвращается `partial`/`resource_limit`, без молчаливого
удаления активной сессии. После перезапуска или истечения TTL нужен новый сбор;
уже показанные пользователю ответы остаются в истории MCP-клиента.

Offline-инструменты с `config_dump` на входе удаляются из публичного контракта.
Внутренние методы анализа принимают только собранные сервером данные. Изменение
контракта и настройки подключения отражаются в README и `get_capabilities`.

### 7.5. Необязательная интеграция с ASTRA-SBT

Интеграция выключена по умолчанию. Для запуска сервера и полного основного
сценария диагностики не нужны ASTRA endpoint, credentials, `projectId` или
соответствие workload проекту ASTRA. При выключенной интеграции сервер не
устанавливает соединения с ASTRA и не предлагает её настройку как обязательный
шаг расследования. Это относится к stdio и Streamable HTTP одинаково.

При явном включении ASTRA дополняет расследование сведениями о зависимостях,
портах, протоколах и требованиях конкретного продукта. Отдельный Go-адаптер
выступает MCP-клиентом внешней системы; встроенная LLM нашему серверу для этого
не нужна. По переданному контракту `/mcp` предоставляет каталог, поиск и чтение,
а `/mcp/agent` — только `agent_loop`; это отдельные подключения. Выбор конкретных
возможностей адаптера не делает оба подключения обязательными для диагностики.

Правила независимости:

- `get_capabilities` показывает, включена ли интеграция и что известно о её
  доступности. Выключенная интеграция не считается ошибкой диагностики.
- Неоднозначное соответствие workload → `projectId` требует уточнения только
  для обращения к ASTRA. Пользователь может продолжить без этого контекста.
- Таймаут, отказ доступа, переиндексация, неподдерживаемый инструмент или ошибка
  ASTRA не прерывают сбор и анализ Kubernetes/Envoy. Обращения ограничены отдельным
  бюджетом времени; результат сообщает о недоступном дополнительном контексте.
- В ASTRA передаётся минимальный необходимый очищенный контекст вопроса;
  полные dump'ы, потоки логов и credentials автоматически не пересылаются.
- Ответ `agent_loop` является текстом, а не гарантированным набором исполняемых
  проверок. Клиентский агент интерпретирует его вместе с фактами; Go выполняет
  только предусмотренные проверки. Текст источников не расширяет права сервера.
- Сведения продукта сохраняются отдельно от runtime evidence, с источником,
  временем получения и известной версией/ревизией. Индекс, рабочая копия и
  развёрнутый образ не считаются одной версией без подтверждения. Ответ ASTRA
  сам по себе не подтверждает причину сбоя и не расширяет cluster-local scope.

## 8. Формат результата

Краткий ответ содержит:

1. Выбранную связь и период.
2. Причину либо прямое сообщение, что она пока не подтверждена.
3. Затронутые pod'ы и основные доказательства.
4. Что рекомендуется исправить/проверить и как проверить результат.
5. Существенные пробелы данных и оставшиеся направления.

Подробный ответ добавляет цепочку пути, таблицу проверок, ресурс с namespace/name,
JSON Pointer к полю, очищенные фрагменты логов, временные метки и альтернативные
гипотезы. Каждое evidence имеет ID, тип источника, UID pod/ресурса, время события
и/или сбора, область применимости и ссылку на конкретную попытку.

Нельзя говорить «всё работает» только по разрешённым конфигурационным ссылкам.
Текущий fail в конфигурации и доказанная причина исторического инцидента — разные
утверждения. Рекомендации адресуются наблюдаемой причине; сервер их не применяет.

## 9. Изменения текущего проекта

| Архивный прототип | Целевое состояние |
|---|---|
| Offline CLI и передача dump через MCP | Только live-сценарий; фикстуры остаются в тестах |
| Один pod и один namespace за сбор | Все реплики участников; cross-namespace в доступной области |
| `istioctl proxy-config all` | Port-forward + фиксированные Envoy GET |
| Нет proxy access logs | Период, парсинг, группировка, корреляция и полнота сбора |
| Отдельные snapshot ID | Пользовательская сессия, очередь и неизменяемые попытки |
| Политики только как контекст | Применимые проверки с явными пределами семантики |
| Однопроксийный trace | Проверка выбранной связи с evidence обеих сторон |
| RBAC с опциональным exec | Logs и port-forward, без exec |
| Только transport stdio | Stdio и Streamable HTTP с одинаковым диагностическим контрактом |

README, architecture, RBAC, CLI/help, Dockerfile и тесты должны соответствовать
единственному live-сценарию. Работа выполняется в существующем проекте, без
создания другого продукта или откладывания согласованного объёма на «следующую версию».

## 10. Критерии приёмки и проверка

- Неоднозначные приложение, namespace, context или направление вызывают уточнение;
  известная пара идёт сразу в расследование.
- Периоды 40 минут, 3 часа и абсолютный интервал одинаково применяются к обеим
  сторонам; default 15 минут не перекрывает пользовательский выбор.
- При нескольких проблемах выбор одной сохраняет остальные и ранее полученный
  результат; `investigated` не означает «исправлено».
- Сбой одной реплики среди нескольких виден отдельно; сбор охватывает весь
  обнаруженный состав, а недоступные pod'ы перечислены.
- Missing route/cluster, пустые endpoints, несовпадение порта, TLS expiry и policy
  denial имеют отдельные случаи проверки с привязкой к evidence.
- Одинаковые порты разных Service и неиспользуемый истёкший сертификат не становятся
  ложной причиной. Timeout и отсутствие destination-логов не доказывают CNI-сбой.
- HTTP 500 от приложения, HTTP 200 с ошибочным gRPC status и TCP transport failure
  не смешиваются в один тип ошибки. При TLS passthrough не заявляются невидимые поля.
- Пустые, неизвестные, частичные, ротированные и previous-логи имеют разные
  объяснения; отсутствие наблюдений не объявляет доступность.
- RBAC deny, HTML вместо dump, неподдерживаемый endpoint, смерть pod'а, отмена и
  превышение лимита дают частичный отчёт и гарантированно закрывают туннели.
- Проверки доказывают отсутствие pods/exec, изменений ресурсов, произвольных
  admin-операций и активных запросов к приложению. Отчёты не раскрывают секреты.
- Старый инцидент при новой конфигурации не получает ложную историческую причину.
- Stdio и Streamable HTTP предоставляют одинаковый набор проверок и состояний;
  удалённый пользователь не может прочитать чужую сессию или evidence по их ID.
- При выключенной ASTRA основной сценарий проходит без её настроек, сетевых
  обращений и вопросов о выборе проекта. При включённой, но недоступной ASTRA
  основной результат сохраняется, а отсутствие контекста продукта явно отмечено.
- В выбранном MCP-клиенте проверяется полный диалог: обнаружение подходящего
  инструмента, уточнение входа, выбор связи, получение результата и продолжение.

Проверка реализации: unit-тесты чистых правил на реалистичных очищенных фикстурах;
контрактные тесты collector на контролируемом runner/HTTP server; MCP сценарии
через stdio; тесты отмены и освобождения port-forward. Затем smoke-проверка на
доступном тестовом Istio-кластере с известными отказами. Пока такого доступа нет,
нельзя объявлять live-проверку на настоящем кластере выполненной.
