# Входное задание агенту-разработчику

[Навигация](README.md) · Статус: handoff проекта; не утверждённый план реализации.

Ты работаешь над существующим Go-проектом `istio-diagnostics-mcp`. Цель —
реализовать описанный здесь live read-only сценарий в текущем проекте.
Рабочая ветка очищена от прежнего сервера; [архив и состав основы](rewrite-baseline.md)
содержат точную точку восстановления. Обратная совместимость старого API не нужна.
Перед изменением продукта прочитай [требования](requirements.md),
[архитектуру](architecture.md), [алгоритм](algorithm.md) и [API](api.md).

## Порядок работы с этим комплектом

1. Сверить чистую основу и фактический статус. Из архива переносить только
   проверенные подходящие функции/сценарии. Не считать проектные tools уже
   реализованными и не переписывать README так, будто проверки пройдены.
2. Разрешить влияющие на реализацию открытые решения O01–O06 из требований.
   Независимую работу не блокировать неизвестным optional ASTRA endpoint.
3. После ревью спецификации подготовить отдельный план реализации с изменяемыми
   компонентами, миграцией публичных tools и проверками. Этот файл не заменяет план.
4. Реализовывать типы и семантику API совместно; при расхождении схемы и текста
   сначала исправить контракт. Не делать тихих несовместимых интерпретаций.
5. Валидировать реальные существенные механизмы: evidence причинности, partial
   coverage, ownership, cancellation, idempotency и all-pod сбор.
6. Для live smoke нужны тестовый кластер и подтверждённые права. До этого
   отмечать «не проверено на кластере», даже если unit/contract tests проходят.

## Ограничения реализации

Не добавлять offline-продукт, exec, активные probes, изменения workload,
обязательную ASTRA или встроенную LLM. Сохранить очистку evidence и limits.
Не реализовывать универсальный shell/HTTP/MCP passthrough под видом диагностики.
Не открывать общий remote endpoint без выбранной и проверенной модели identity.

Статические фикстуры допустимы для тестов. Продуктовые результаты получают
только live-сбором. Нет требования добавлять постоянную БД, кластерный оператор
или собственный UI для выполнения согласованного сценария.

## Что предъявить при завершении реализации

Рабочие tools по контракту, обновлённые инструкции подключения, результаты
meaningful tests, известные ограничения, статус live-проверки и миграция старых
инструментов. Подтверждение исправления ошибки требует воспроизводимого результата,
а не только ссылки на issue или убедительного текста LLM.
