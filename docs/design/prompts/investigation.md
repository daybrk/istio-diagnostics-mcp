# Ведение расследования

Вход: diagnosis_id, состояние, jobs, coverage и next_actions.
Результат: исследованная связь или объяснение, каких данных не хватает.

1. При queued/running читай `get_diagnosis` с умеренным polling. Чтение не требует
   нового operation_id и не должно перезапускать сбор.
2. При awaiting_selection покажи источник, назначение, port/protocol, сигнатуры,
   observation count и затронутые pod'ы. Уточни, что count относится к записям,
   если сервер не сообщил надёжную дедупликацию запросов.
3. Передай выбранный connection_id в `investigate_connection`. Не выбирай вместо
   пользователя при нескольких направлениях. Для исходно указанной точной пары
   не навязывай дополнительный выбор.
4. Оцени coverage по всем репликам. Чтение 7 из 8 pod'ов не равно полному охвату;
   покажи недоступную реплику и причину. Не проси «проверить один pod вместо всех»
   только ради уменьшения объёма.
5. Если proxy не готов или dump недоступен, используй предоставленные статусы,
   Events и диагностические/previous logs. Не требуй исправить proxy до начала
   расследования и не запрашивай exec как обход.
6. По findings при необходимости получи конкретные `get_evidence`. Не выгружай
   все dump'ы в контекст. Различай source и destination, Service port и targetPort.
7. Для объяснения причины используй [evidence](evidence.md), для ответа — [report](report.md).

Нельзя завершить расследование фразой «сеть исправна», если нет access events.
Допустимый ответ: неудачное соединение не наблюдалось; доступные конфигурационные
проверки дали такие результаты; для подтверждения нужно повторить обращение и
собрать новое окно. MCP не отправляет тестовый запрос.

Не повторяй один и тот же tool с теми же данными ради нового объяснения. При
конфликте operation_id используй существующий job или новый ID для новой операции.
При unknown/unsupported сохрани границу вывода; не пытайся заменить неподдержанный
evaluator собственным уверенным заключением по одному фрагменту YAML.

На просьбу остановиться вызови `cancel_operation` для работы, если пользователь
хочет сохранить результат, либо `close_diagnosis`, если хочет закончить сессию.
При смене задачи уточняй только существенную неоднозначность, не теряй очередь
предыдущего расследования, пока сессия доступна.
