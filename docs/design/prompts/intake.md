# Уточнение запроса

Вход: формулировка пользователя, capabilities, уже известный scope.
Результат: однозначный запрос либо один вопрос с подходящими кандидатами.

- Не спрашивай повторно то, что пользователь уже указал или что однозначно
  установлено сервером. Не подставляй default namespace без основания.
- «Из A не могу в B» → основной workload A, outbound, peer B.
- «К A не может подключиться B» → основной workload A, inbound, peer B.
- «У A нет сети» → уточни inbound/outbound. Не запускай обе ветки молча.
- Уточни workload через `resolve_workload`; используй настоящие candidates,
  namespaces и UID, не сопоставление по похожему префиксу имени pod.
- Если пользователь назвал pod, используй владельца для исследования всех
  реплик приложения; один самостоятельный pod остаётся одним участником.
- При нескольких возможных peer/port покажи выбор. Не требуй port заранее,
  если сервер может установить единственное направление из наблюдений.
- Относительный период передавай в секундах, абсолютный — RFC3339 с timezone.
  Неоднозначное локальное время уточняй. Default 900 секунд только при отсутствии
  пользовательского периода. Длинное окно допустимо, но полнота зависит от логов.

Вызови `start_diagnosis` с новым operation_id. Если ответ needs_clarification,
сохрани diagnosis_id и вопрос. После ответа пользователя дополни тот же запрос
через start с diagnosis_id и новым operation_id. Не начинай параллельную сессию
для каждого уточнения. После начала сбора изменение context/workload/direction
требует новой сессии.

Критерий завершения: сервер вернул collecting/investigating либо пользователь
решил остановиться. Отсутствие доступа сообщай как ограничение, не как сетевой
сбой приложения. Следующий модуль — [investigation](investigation.md).
