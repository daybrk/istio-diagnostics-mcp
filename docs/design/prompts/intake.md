# Уточнение запроса

Вход: формулировка пользователя, capabilities, уже известный scope.
Результат: однозначный запрос либо один вопрос с подходящими кандидатами.

- Не спрашивай повторно то, что пользователь уже указал или что однозначно
  установлено сервером. Не подставляй default namespace без основания.
- «Из A не могу в B» → основной workload A, outbound, peer B.
- «К A не может подключиться B» → основной workload A, inbound, peer B.
- «У A нет сети» → уточни inbound/outbound. Не запускай обе ветки молча.
- Уточни workload через `resolve_workload`; используй настоящие candidates,
  namespaces и UID, не сопоставление по похожему префиксу имени pod.
- Если пользователь назвал pod, используй подтверждённого сервером владельца
  для исследования всех реплик приложения. Не угадывай Deployment по имени pod
  или selector по имени приложения. Если resolve вернул только Pod, передавай
  его; отсутствие подтверждённого владельца обозначь как ограничение охвата.
- При нескольких возможных peer/port покажи выбор. Не требуй port заранее,
  если сервер может установить единственное направление из наблюдений.
- Относительный период передавай в секундах, абсолютный — RFC3339 с timezone.
  Неоднозначное локальное время уточняй. Default 900 секунд только при отсутствии
  пользовательского периода. Длинное окно допустимо, но полнота зависит от логов.

Дождись `resolve_workload`, затем используй выбранный candidate в
`start_diagnosis`: поля kind/name/namespace/context; UID из результата не входит
в WorkloadQuery. Не начинай start параллельно с разрешением неоднозначного workload.
Если цель вроде «kubernetes» неоднозначна, уточни, имеется ли в виду API-сервер
и какой Service/hostname используется. Не назначай namespace `default` без
подтверждения. Если подтверждённый peer за пределами capabilities.scope,
сообщи ограничение; не маскируй Service под host ради обхода scope.

Вызови `start_diagnosis` с новым operation_id. Если ответ needs_clarification,
сохрани diagnosis_id и вопрос. После ответа пользователя дополни тот же запрос
через start с diagnosis_id и новым operation_id. Не начинай параллельную сессию
для каждого уточнения. После начала сбора изменение context/workload/direction
требует новой сессии.

## Формат аргументов и ошибки вызова

`workload`, `peer`, `time_window` передавай объектами, без внешних кавычек.
Пример формы запроса (имена и scope замени подтверждёнными значениями):

```json
{
  "operation_id": "start-unique-id",
  "workload": {"kind": "Pod", "name": "worker-1", "namespace": "shop", "context": "test-cluster"},
  "direction": "outbound",
  "peer": {"kind": "service", "value": "backend", "namespace": "shop"},
  "time_window": {"lookback_seconds": 900}
}
```

Совместимость: сервер допускает однократно JSON-кодированную строку объекта в
этих трёх полях start и в time_window refresh. Это не свободный текст: после
декодирования действуют те же обязательные поля, типы и ограничения.

При `must be object`, `must NOT be valid`, `InvalidParams` или другой ошибке
валидации сначала сравни фактические arguments с опубликованной схемой. Не
делай вывод о лишнем selector только по сообщению `must NOT be valid`: строка
может провалить условный JSON Schema раньше проверки содержимого объекта.
Разрешена одна повторная попытка с исправленным форматом. При повторном отказе:

- Прекрати вызовы, не относящиеся к устранению блокера. Сообщи, что сбор не
  начался, если нет успешного старта. Не сообщай причину сетевого отказа.
- Сохрани исходные workload/peer/direction/window и полученный diagnosis_id.
  Не перебирай Pod/Deployment/Selector, не удаляй peer, namespace или период,
  не заменяй «последние 15 минут» выдуманными абсолютными timestamp.
- Покажи инструмент, проблемное поле и очищенную от секретов ошибку. Уточни
  название/версию клиента и модели, если они неизвестны; предложи обновление
  бинарника и перезапуск клиента для загрузки схем.
- Не закрывай и не создавай сессии ради обхода ошибки формата. После устранения
  блокера продолжи тот же needs_clarification diagnosis с новым operation_id.
- Не используй ASTRA, shell/kubectl или активные probes вместо неудавшегося
  MCP-сбора. ASTRA не исправляет сериализацию и не подтверждает состояние кластера.

Критерий завершения: сервер вернул collecting/investigating либо пользователь
решил остановиться. Отсутствие доступа сообщай как ограничение, не как сетевой
сбой приложения. Следующий модуль — [investigation](investigation.md).
