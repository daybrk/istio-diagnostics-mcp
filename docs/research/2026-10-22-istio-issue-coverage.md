# Покрытие диагностики: предварительный разбор Istio issues

Дата исследования: 22 октября 2026 года.
Проект: `istio-diagnostics-mcp`, Go.
База сравнения: код `45ea784` и проектное описание `b96a082`.
Статус: исследование и рекомендации; новые рекомендации не означают, что они
уже реализованы или утверждены как расширение спецификации.

## Вывод

Предлагаемый сбор достаточен для сильной диагностики конфигурационных отказов и
полезной локализации runtime-ошибок. По публичным issue нельзя честно получить
процент покрываемых production-инцидентов: здесь нет ни репрезентативного
распределения причин, ни прогона нашего сервера на воспроизводимых отказах.

Главный найденный пробел — ориентация спецификации на access logs. Нужно отдельно
разбирать уже доступные служебные сообщения Envoy/pilot-agent из `istio-proxy`.
При сбое запуска прокси access logs и рабочий config_dump могут отсутствовать.

## Метод

Через поиск и GitHub API просмотрены описания 21 issue. Для восьми дополнительно
прочитаны содержательные комментарии: #52847, #25832, #55138, #27831, #56865,
#60326, #57889, #50186. Для расширенной матрицы отобраны 12 случаев, влияющих на
sidecar и внутренние соединения либо готовность обслуживающего их прокси.
Два других случая используются как защита от ложных выводов; семь — как
исторические аналоги или примеры за пределами объёма. Список приведён ниже.

Выбор целевой, по разнообразию механизмов: listeners/порты, политики, endpoints,
mTLS, reset, запуск, SDS/CA, DNS и CNI. Это не случайная выборка из всех issue.
Трекер содержит сложные баги, вопросы использования, несколько независимых
проблем под одной темой и автоматически закрытые обращения. Closed не означает
исправление; предположение автора не считается установленной причиной.
Старые issue используются как сценарии тестирования, а не доказательство
наличия того же дефекта в современной версии Istio.

Оценка ниже — экспертное сопоставление доступных сигналов с проектом, не результат
запуска MCP. Уровни: обнаружить симптом; локализовать механизм/участок; подтвердить
непосредственную причину; установить глубинный дефект. Последние два уровня
разделены: отказ проверки сертификата ещё не объясняет поломку его обновления.

успешно диагностированных инцидентов. Сценарии не воспроизводились.

## Что уже есть в коде и чего ещё нет

Просмотрены `internal/diagnostics/{analyze,trace,tls}.go`,
`internal/live/diagnose.go`, регистрации MCP tools и существующие тесты.
Есть статический trace одного Envoy, missing cluster refs, отдельные route/filter
chain conflicts, xDS error_state/warming, явные пустые endpoint assignments,
readiness, наличие Service endpoints и срок доступного публичного сертификата.

Нет сбора и корреляции proxy logs, проверки обеих сторон с all-pod охватом,
effective policy evaluation и очереди диагностической сессии. Проверки источников
конфликтующих ресурсов, TLS runtime и истории состояния ограничены. Наличие
unit-теста на локальное правило не считается воспроизведением соответствующего
публичного issue. В этом исследовании Go-тесты не запускались: код не менялся.

Согласованный дизайн существенно расширяет эту базу. Пока реализация и испытания
не завершены, приписывать ему уже достигнутую долю покрытия нельзя.

## Рекомендуемые уточнения текущего дизайна

1. **Два потока из `istio-proxy`.** Access events и служебные сообщения Envoy/
   pilot-agent. Правила для SDS, CSR, xDS rejection, invalid JWKS, startup/drain
   и ошибок handshake. Читать текущие и доступные previous-логи; не включать debug
   автоматически. Если нужное сообщение появляется только в debug, фиксировать
   недостаток наблюдаемости.
2. **Ветка «proxy не готов».** До обязательного dump и поиска failed requests
   проверить наличие/injection, container/initContainer status, restart reason и
   доступные startup logs. Возвращать диагностику этой ветки даже при недоступном
   порте 15000. Она не должна завершаться пустым списком направлений.
3. **Kubernetes Events и минимальные metadata.** Связать с UID и временем pod'а,
   учитывать revision, namespace labels, rollout/deletion/termination. События
   ограничены хранением и сами по себе не доказывают причинность.
4. **Выборочные runtime counters.** Рассмотреть ограниченный GET `/stats` для
   выбранного cluster/listener: connect failures, resets, overflow, TLS и outlier
   counters. `/clusters` и `/certs` уже предложены. Разность двух показаний
   относится только к интервалу между ними; текущий counter не является историей
   за выбранные пользователем 40 минут. Смена процесса/сброс counter учитывается.
5. **Связь с известными issue.** Совпадение версии, сигнатуры и топологии даёт
   ссылку «похожий случай», не автоматически `confirmed`. Нельзя советовать
   workaround из старой темы без проверки применимости к версии и симптомам.

Пункты 1–4 сохраняют live read-only, но конкретные endpoints, ресурсы и правила
следует внести в спецификацию после согласования. Чтение istiod/CoreDNS/CNI-логов,
node state, приложения, exec или активные probes автоматически не добавляются.
Отдельный LLM-агент на сервере не заменяет отсутствующие данные.

## Как получить измеримое покрытие

Создать начальный набор из 30–50 воспроизводимых сценариев. Включить базовые ошибки
Service/targetPort/selectors/subsets, routing, TLS и policies, выбранные сложные
issue, а также здоровые и намеренно неполные случаи. Разделить сценарии для
разработки правил и отдельную проверочную выборку. Отдельно фиксировать версии
Istio/Envoy, источник исходного сценария и доступный серверу набор наблюдений.

Для каждого сценария записать ожидаемый симптом, непосредственную причину,
допустимые неизвестные и запрещённые ложные объяснения. Выполнять диагностику
тем же live-сборщиком, который будет использовать пользователь. Фикстуры служат
unit-тестам и не являются возвращением offline-продукта.

Метрики считать раздельно: обнаружение сбоя; локализация участка; подтверждение
причины; precision заявленных подтверждённых причин; корректное воздержание при
неполных данных; время, объём и число обращений к API. В знаменатель покрытия
класть только случаи согласованного scope; внешние/ambient случаи отражать отдельно.
Не давать успешному обнаружению HTTP 503 тот же балл, что доказанной причине.
